# Деплой и проверка в EDT

## Деплой

Единственный путь — скрипт (EDT при деплое **закрыта**):

```bash
bash scripts/deploy-edt.sh --edt "<инсталляция>/1cedt" --workspace "<ws>"
# Для приёмки использовать сохранённый p2 нужного прогона:
bash scripts/deploy-edt.sh --repo "<сохранённый-p2>" --edt "<инсталляция>/1cedt" --workspace "<ws>"
```

- Скрипт сам: снимает прежнюю копию (или p2 делает update), ставит
  `com.e1c.v8codestyle.feature.feature.group`, сверяет **все** бандлы
  `com.e1c.v8codestyle*` с `bundles.info` (anti-stale по квалификатору),
  дочищает устаревшие jar пула, чистит журнал воркспейса.
- JavaSE-guard: сверяет EE собранных бандлов с `requiredJavaVersion`
  инсталляции (читает и BREE, и Require-Capability — Tycho 5 пишет второе).
- Деплой **заменяет комплектную копию** (те же IU-имена). Откат — только
  восстановлением из дистрибутива EDT.

## Ловушки (проверено болью)

- **pgrep-самострел**: если в inline-команде с `pgrep -f` встречается тот же
  путь текстом (в присваивании, в запуске) — шелл убивает сам себя. Скобочный
  трюк `[1]cedt` защищает только сам паттерн; **пути собирать конкатенацией**:
  `P="1C_EDT 202""6.2/1cedt"; pgrep -f "$P"`. Деплой-скрипт безопасен (паттерн
  в файле), опасны именно inline-команды.
- Разрешение рестарта привязано к экземпляру/стенду, не всем EDT. Пользователь
  разрешил агентские deploy/smoke в `~/edt/apk_2026`; сверять PID/время запуска/
  installation с известной сессией. Чужую открытую сессию не закрывать,
  незаписанные данные не считать сохранёнными. Предпочитать штатное закрытие.
- Перед deploy сохранить журнал в уникальный `/tmp/opencode`-файл: скрипт
  чистит исходный log. Сохранённый p2/source snapshot и установленный qualifier
  должны совпадать; «последний target» после другого clean не доказательство.
- Native launcher `1cedt` и дочерняя Java — разные PID. Завершение launcher
  само по себе не доказывает останов JVM. Записать PID/время/команду при старте,
  перед stop проверить принадлежность обоих процессов; после stop повторный
  безопасный pgrep и проверка workspace lock. Не запускать director, пока
  JVM той же установки жива. Свой Xvfb завершать только после EDT.
- Системный DISPLAY может остаться от завершившейся удалённой сессии.
  Перед стартом проверить `xdpyinfo` с тем же DISPLAY/XAUTHORITY. При отказе
  не приписывать `gtk_init_check() failed` плагину и не менять глобальную
  X-аутентификацию: сохранить лог, для агентского smoke использовать свой
  Xvfb с auth. Не выдавать его за проверку рабочего стола пользователя.
- При удалении стороннего коннектора брать точный root feature IU из
  актуального p2-профиля. Удалять director'ом на закрытой EDT, не ручным rm
  JAR из общего пула. Проверить отсутствие bundle в bundles.info и сохранность
  v8cs/MCP. Старые сохранённые маркеры — отдельный вопрос revalidation/clean,
  не доказательство того, что uninstall не сработал.

## Запуск EDT (критично: правильная JVM)

| Инсталляция | -vm |
|---|---|
| EDT 2026.2.2 (`~/edt/apk_2026`, MCP edt_apk) | **`/opt/1C/1CE/components/axiom-jdk-full-25.0.4+5-x86_64`** (полная Java 25: JavaFX + jshell) |

Запуск: `1cedt -vm <путь>/bin/java -data <ws> -nosplash`. Прямой запуск без
`-vm` подхватывает системную java → EDT сыплет чужими ошибками (ai.ui,
workbench, JavaFX) — не путать с нашими.

Почему полная Java 25 для 2026.2: AI-плагин EDT (`com.e1c.edt.ai.ui`) строит
**карточки замечаний всех провайдеров** через Guice; на неполной JVM он падает
(без FX — `javafx/scene/Node`, на JRE — `jdk/jshell/spi/…`), а `bsl.ui 24.0.0`
не изолирует contributor'ы → карточки ломаются у v8-cs и коннектора одновременно.
Сам диагноз — по стеку `AIMarkerHoverContributorFactory` в журнале воркспейса.

## Триаж после smoke

**Сначала MCP EDT (28.10, решение пользователя).** Перед каждым новым
сценарием проверить актуальные tools и guide: возможности MCP меняются.
Подтвердить version/list_projects paths; модель, маркеры, incremental и
доступные координаты читать/проверять штатными MCP-инструментами. Не обходить
доступный инструмент локальным HTTP-клиентом или UI-автоматизацией. UI —
только оставшийся неподдерживаемый MCP пункт с явно названным ограничением.
Старые сведения «MCP не умеет offsets/карточки» без проверки текущего guide
не основание для UI. Описания собственного каталога MCP отличать от карточки
в EDT; строки/count отличать от точных ranges.

### Запись smoke-кода через MCP

`project_checks` writes требуют пользовательского consent. На невидимом Xvfb
диалог может остаться pending после timeout клиента; read-back не завершает
исходный запрос. Не повторять set вслепую, не нажимать собственный Allow и не
обходить gate через cset/UI. Для приёмки on/off использовать desktop, доступный
пользователю, и сохранять before/after/persisted. Consent на enable не считать
автоматическим согласием на новые операции/профили; восстановление также через
штатный gate. Clean может сменить shortUid — для restore использовать полный
checkId|contributorId, не старый SU-код.

1. Сохранить baseline bytes/hash и прочитать модуль через MCP. Для точечных
   правок предпочитать searchReplace с уникальным oldSource и expectedHash;
   не использовать overwrite=true вместо проверки текущего текста.
2. `write_module_source` проверяет синтаксис и может нормализовать запрещённые
   символы; при проверке точного текста задавать normalizeInvalidCharacters=false.
   Сохранять результат записи, не считать его доказательством завершённой
   валидации — далее читать конкретные маркеры/строки.
3. При `mutationCommitted:true` текст уже записан: сначала перечитать состояние,
   не повторять append. Ошибка экспорта extension-state и ошибка BSL-детектора
   не одно и то же. Дополнительные действия — по актуальному guide инструмента.
4. После bad/fix/bad убрать только свой фрагмент с guard. MCP нормализует
   окончания строк, поэтому отдельно сравнить baseline bytes/hash; нельзя
   обещать byte-exact restore только по совпадению количества строк.
   Если обнаружена чужая правка — остановиться, не затирать baseline целиком.

### Описания, якоря и журнал

- В MCP2.21.1 CheckDescriptionLoader читает собственный bundle/override-каталог,
  а не HTML v8cs. Поэтому `Has docs=false`/`No check description` не доказывает
  поломку EDT-карточки. На другой версии заново проверить guide/реализацию.
  Наличие check.descriptions/{ru/,}<id>.html в installed JAR доказывает упаковку,
  UI settings — отрисовку описания, F2-hover — открытие карточки маркера;
  не подменять одно другим.
- Нормативку и объяснения искать через MCP v8std: exact diagnostic ID →
  v8std_explain_diagnostics → v8std_get_page. Если новый v8cs ID пока unknown,
  использовать подтверждённый LS mapping из реестра, с оговорками partial
  scope. Unknown в корпусе не означает отсутствия проверки. v8std не выполняет
  EDT-валидацию и не доказывает открытие карточки UI.
- В EDT-MCP2.22.1 get_form_screenshot доступен после явного включения;
  пользователь включил его на стенде28.10. Для bounds сначала layout snapshot;
  screenshot использовать по визуальной задаче, не менять startup render flags
  без нужды. Статус enabled инструмента и наличие buffer flag — разные условия.
- Для CFG all-paths якорь — имя функции; unreachable — первое мёртвое
  утверждение блока. Предупреждение unused-variable на том же присваивании
  имеет другой инвариант и не является дублем CFG. В F2 возможен общий hover
  нескольких замечаний — сверять конкретные сообщения/CheckUid.
- После upgrade первый startup может дать Unknown check id; сохранить его
  отдельно. Restart + clean и latest-session Unknown=0 подтверждают рабочий
  повтор, но не исправление платформенного дефекта. Navigator/secure-storage/
  RightsIndexBuilder ошибки не смешивать с OURS; не объявлять весь лог чистым.
- Сравнивать не только qualifier, но по возможности SHA-256 всех установленных
  v8cs JAR с saved p2. Qualifier vyyyyMMdd-HHmm может отражать UTC при другом
  локальном часовом поясе: не считать артефакт stale только из-за часов в имени.

Сценарий приёмки для конкретного нового/изменённого чека:
1. Initial `clean_project` после установки новой регистрации. Проверить
   expected bad/clean objects, count и ranges; не общий project «без ошибок».
2. Изменить уже существующее значение **без clean**: bad→fix→исчез,
   clean→bad→появился. Отдельно parent flags/localized entry/reference types
   если они влияют на алгоритм. `modify_metadata` stale выдача ещё не pass —
   перечитать markers и проверить фактический результат.
3. Финальный clean и журнал. Если incremental failed, нельзя засчитать
   clean0 как замену: красная regression→fix→source gate→новый артефакт→повтор.
4. Если заявлено несколько owners (module/DCS/dynamic list), каждый проверить
   своим примером; synthetic owner в test не заменяет native bridge dispatch.

Для SWT/AT-SPI crash известного стенда использовать `NO_AT_BRIDGE=1` при
запуске приложения/тестов; pyatspi automation не совмещать с itests.

1. Квалификатор в `bundles.info` инсталляции = свежесобранный.
2. Журнал: `tr -d '\r' < <ws>/.metadata/.log | grep -c '^!ENTRY .* 4 '`,
   затем агрегат: `grep -A1 '^!ENTRY .* 4 ' | grep '^!MESSAGE' | sort | uniq -c | sort -rn`.
3. Триаж: OURS-real (чинить) / OURS-noise (правильный уровень/logging) /
   PLATFORM (записать, идти дальше). Требование — нет новых наших ошибок,
   не «0 упоминаний v8codestyle»: ожидаемые INFO hub/dedup допустимы.
   Startup Unknown check id сохранять, не маскировать: restart+clean,
   latest session с0 повторений; продолжение исключений — реальный блокер.
4. GUI-минимум: «Установленное ПО» → свежий квалификатор; «Свойства проекта →
   Проверки» — список на месте; карточка замечания открывается с текстом.
