# AGENTS.md — форк v8-code-style (malikov-pro)

Форк [1C-Company/v8-code-style](https://github.com/1C-Company/v8-code-style) —
проверки «1С:Стандарты разработки» для 1C:EDT на фреймворке
`com.e1c.g5.v8.dt.check`. База для собственных проверок; родительский проект —
соседний `bslls-connector-for-edt` (канал диагностик BSL LS). Общие правила
каталога — в `../AGENTS.md`.

## Процесс (обновлено 12.10)

- **Ветки**: `develop` — интеграция; фичи/пачки — `feature/*` от `develop`;
  merge `--no-ff` в `develop` после зелёного прогона. `master` — только под
  релиз: merge из `develop` + тег `X.Y.Z` **по явной команде пользователя**.
- **Пачки**: основная пачка — до 10 проверок; рабочая мини-пачка — 2–3
  связанных проверки одного канала. Каждой — собственные тесты/учёт;
  итоговый гейт канала общий для стабильного снимка мини-пачки. Первый
  незнакомый API/канал доводить вертикально до живой детекции, затем группировать.
- **Верификация по радиусу поражения**: итерация — целевые тесты своего
  чека и соседей; перед интеграцией — весь затронутый itests-модуль на
  **обеих платформах**; полный `compile.sh` — раз в основную пачку,
  при изменениях общей инфраструктуры/зависимостей и перед релизом.
  Если мини-пачка затрагивает два канала, гейт нужен каждому каналу.
- **Документальные правки**: после изменения только markdown/messages-
  текста достаточно целевого `CheckDescriptionTest` канала и проверки
  generated индексов. Не повторять весь модуль ради карточки. Изменение
  регистрации, параметров, локализационных ключей или зависимостей — уже
  не «только текст»; новые данные о дефекте также расширяют гейт.
- **Незнакомый API**: сначала рабочий пример в репозитории + `javap`/
  MANIFEST (сигнатуры, доступность пакета), затем минимальный research-тест
  на один вопрос. Не придумывать enum/фабрики/fluent-builder цепочки.
- **Один Maven в checkout, стабильный снимок**: пока сборка идёт,
  не менять source/tests/fixture/build-скрипты и не запускать второй Maven.
  Можно читать исходники следующего кандидата, писать внешние заметки и
  готовить изолированный smoke через MCP. Не sleep/poll фоновые сборки;
  дождаться уведомления. При правках после старта результат не относится
  к финальному снимку — повторить затронутую проверку.
- **Свидетельства гейта**: записывать commit + diff/хеш снимка (включая
  untracked-файлы), платформу, команду, код завершения, время; агрегировать
  XML tests/failures/errors/skipped по реально пройденным модулям. Сохранить
  p2 нужного профиля **до** clean/сборки второго профиля; установить именно
  сохранённый артефакт, сверить квалификатор. Текущие скрипты не фиксируют
  всё автоматически: отчёт собирать явно, не выдумывать существующую автоматизацию.
- **Приёмка включает инкрементальность с первого теста**: нарушение →
  исправление → маркер исчез; чистое → нарушение → появился; изменение
  существующего значения, а не только создание/удаление. Если результат
  зависит от родителя/языковой записи/связанного объекта — тестировать и
  его изменение. Проверять конкретные объекты, диапазоны и отсутствие дублей,
  не только общий count. Live-приёмка — сначала изменение **без clean**,
  затем полная перестройка и журнал; первоначальный clean после установки
  нового чека нужен отдельно. Сборка не заменяет живую проверку.
- **Отчёты**: один актуальный блок «состояние / доказательства / следующий
  шаг» в начале; ниже краткий журнал этапов. Устаревшие статусы явно
  исторические; не накапливать цепочку противоречащих «сейчас выполняется».
  Готово в feature, влито в develop, установлено и выпущено — разные состояния.
- При работе над issue/PR, создании и завершении связывать его с сессией
  через `openchamber session.link`, если действие доступно; при отсутствии
  инструмента явно записывать URL и ограничение. Не создавать PR лишь для ссылки.
- Эти runtime-гейты относятся к продуктовым изменениям. Для правки только
  AGENTS/CLAUDE/skills проверять diff, ссылки/пути, структуру Markdown и
  согласованность правил; Maven/deploy/live не нужны. Обновление инструкции
  об автоматизации не означает, что новые scripts уже реализованы.
- **10.10: зелёный гейт не доказывает полноту пачки.** Четыре готовые
  feature-проверки №12 не попали в интеграцию, но гейт прошёл без них.
  Перед merge сверять исходные feature-коммиты с фактическими классами
  и регистрациями: `python3 scripts/audit-check-integration.py
  --source-commit <sha> ...`. Скрипт разбирает plugin.xml, ловит склейки,
  дубли и отсутствующие исходники; учитывает cherry-pick (одной проверки
  git ancestry недостаточно). Tracking «готово» отличать от «влито».

## Платформы и сборка

- **Основная цель — EDT 2026.1** (рабочая платформа); **EDT 2026.2** — пре-релиз.
  Один исходник на обе платформы: бандлы собираются как **JavaSE-17**
  (JVM 17 → JVM 25 совместим снизу). BREE обратно на 25 не поднимать.
- Вход — `bash compile.sh`:
  - без флагов — EDT 2026.1 (таргет `targets/edt-2026.1`, ruby/2026.1);
  - `--profile edt-2026.2` — пре-релиз (таргет `targets/default`, ruby/2026.2);
  - `--skip-tests` — быстрые итерации; полный прогон itests ~35 мин;
  - `--full` — в точности CI апстрима (`-PSDK,find-bugs`).
- Тулчейн без sudo: JDK 25 — `~/tools/jdk-25.0.4.1+1` (только тулчейн сборки),
  Maven 3.9.9 — `~/tools/apache-maven-3.9.9`.
- Апстрим собран под JavaSE-25/EDT 2026.2; отличие форка от master:
  `bom/pom.xml` (компилятор 17, EE 17, свойство `edt.target.artifact`,
  профиль `edt-2026.2`), все `MANIFEST.MF` (BREE 17), `targets/` (модуль
  `edt-2026.1`). Это осознанный дифф — при синке с апстримом эти места
  переносить руками, не откатывать.

  На EDT 2026.1 — axiom-jdk-full-17 из комплекта.
- Не удалять jar из `~/.p2/pool` при работающей EDT (CNFE в рантайме).
- **Стенды (изменено пользователем 30.09)**: `rt_test` и `2026_test` удалены.
  Активный воркспейс — **АПК** (`~/edt/apk`, EDT 2026.1.3.25, MCP `edt-apk`):

## Особенности репозитория

- Сборка перегенерирует `docs/checks/*` и карточки (индекс проверок) —
  изменения этих файлов после сборки нормальны, коммитить вместе с правками.
- Версию читать из текущего pom, не фиксировать устаревающий SNAPSHOT в
  инструкции; квалификатор `vyyyyMMdd-HHmm` из времени сборки.
- itests поднимают OSGi-рантайм с тестовым проектом (база — `CheckTestBase`
  из EDT); при сборке под 2026.1 следить, чтобы тестовая фича EDT резолвилась.
- **AST-вердикты перепроверять на чистом синтаксисе**: отдельно проверять
  syntax errors node model, отдельно recovery-кейсы. 10.10 прежний отказ
  DoubleNegatives опровергнут AstNegationResearchTest на обеих платформах:
  NOT(NE)/NOT(NOT) со скобками корректны; NOT NOT без скобок — syntax error.
  Исследовательский тест не заменяет tests продуктовой диагностики.
- data-exchange-load: не засчитывать текстовое упоминание обращения внутри
  строк/комментариев как проверку. NOT(load) доступен в AST обеих платформ;
  regex-fallback удалён после красного regression (expected2/actual0).
  Case-insensitive TreeSet нельзя копировать Set.copyOf — comparator теряется.
- **10.10: живой дедуп проверен через настоящий applyChanges** в EDT2026.1:
  fine off→on при dedup=true выключает coarse с INFO, после clean fine1/coarse0.
  Явное coarse on уважается, fine off не включает coarse обратно, dedup off
  не вмешивается. Прямой onChange в itest не заменял этот smoke.
- **AT-SPI automation опасна для SWT этой EDT**: обход pyatspi спровоцировал
  native crash в gtk_widget_is_sensitive/AccessibleObject.atkObject_ref_state_set
  одновременно в живой и тестовой JVM. Не смешивать AT-SPI/UI automation с
  itests; для восстановления прогонов использован NO_AT_BRIDGE=1. Не путать
  crash платформы с assertion failure, сохранять hs_err.
- Form-itests: `getMarkers(formId)` читает только маркеры самой формы;
  для замечаний групп нужен `getNestedMarkers` с фильтром CheckUid.
  Не совмещать обход формы с containment-якорем групп: появляются дубли.
  Для зависимостей от родительских свойств использовать generic context
  collector с явным FORM top-filter: обычный collector молча отбрасывается,
  если его EClass не входит в supported top/containment (00136, 10.10).
- QL-itests на `AbstractQueryTestBase` использовать с `QlFullDemo`:
  его `enableCleanUp=false` оставляет проект; `QlEmptyProject` затем
  конфликтует с `SingleProjectReadOnlyCheckTestBase` (resource already
  exists). Точечный зелёный тест этого не ловит — нужен весь ql-модуль.
- QL `IQlResultAcceptor.addIssue(message)` якорится на начале запроса,
  не на текущем delegate-объекте. Для точной позиции — EObject+feature
  или `addIssue(message, line, offset, length)` по QL node model;
  модульный мост сам переносит координаты. OR без собственной фичи
  якорить на Keyword ИЛИ/OR (LogicalOrIssueLocation, smoke 10.10).

## Управление проверками из кода (API настроек, EDT 2026.2)

Фреймворк `com.e1c.g5.v8.dt.check.settings` даёт полный цикл **программного**
управления проверками на уровне проекта (декомпиляция 6.0.102):

| Операция | API |
|---|---|
| Чтение настройки | `getSettings(CheckUid, IProject)` → `ICheckSettings`: `isEnabled()`, `setEnabled(bool)`, `setSeverity`, параметры |
| Запись | `applyChanges(Collection<ICheckSettings>, IProject)` — сохраняет и перезапускает валидацию |
| id ↔ UID | `getCheckUidForCheckId("id", project)` / `getUidForShortUid` / `toUid` (UID = plugin id + check id) |
| События | `addChangeListener(ICheckSettingsChangeListener)` / `removeChangeListener` |
| Профили валидации | `getAvailableSettingsProfiles`, `getActiveSettingsProfile`, `setActiveSettingsProfile`, `import/export/duplicate/rename/deleteSettingsProfile` — настройки живут профилями, applyChanges пишет в активный |
| Массовые правки | `setMassiveCheckProcessDisabled(true, project)` → пачка правок → `false` |
| Динамические проверки | `registerChecks/unregisterChecks(ICheckProvider)` (+ `CheckInfo`) — кодом, без extension point |

**Дедупликация** («включили точную — погасить грубую»), принципы:

1. По событию `addChangeListener`, НЕ «при старте»: при старте проекты не
   загружены; ранний вызов — «не знаю» без кэширования, дефолт = прежнее
   поведение (образец — `LsProjectGate` коннектора, issue #26).
2. Однонаправленно: гасим грубую при включении точной; обратно никогда
   не включаем (пользователь мог выключить сознательно).
3. Опционально и прозрачно: выключатель в настройках, дефолт — ничего не
   трогаем; каждое автогашение — INFO в журнал.
4. Анти-пинг-понг: игнорировать изменения, порождённые самим дедупликатором.
5. Таблица пересечений: статья v8std → проверка v8-cs ↔ код LS ↔ (будущее)
   проверка АПК. Каталоги обеих сторон уже есть.

`v8codestyle.qlHubAutoEnableDisabled` (tests/pom.xml vmargs) глушит фоновые
триггеры — асинхронное включение рестартует валидацию и гонит тесты, читающие

`ensureEnabled` напрямую. Грабли: `getSettings` для неготового профиля
возвращает ДЕФОЛТЫ (не бросает); `POST_OPEN` не существует — только
`POST_CHANGE`+флаг OPEN; Guice требует `@Inject`.
